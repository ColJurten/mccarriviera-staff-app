# Database migrations

US-006 part 1; ADR-0006/0007/0011/0019/0022/0023/0024. Ordered dbmate
migrations create the 18 business tables on PostgreSQL 17. All have UUID primary keys,
`created_at` and a `created_by` foreign key to `staff_profiles`.

Load the external local configuration as described in [deploy](../deploy/README.md).
From the repository root:

```sh
pnpm db:migrate
export DB_DISPOSABLE=1 # isolated synthetic local/test database only
pnpm db:seed
pnpm test --filter db
pnpm db:generate
pnpm db:check
```

`MIGRATION_DATABASE_URL` is the `mcr` database owner connection, used only by
migration, seed, code-generation and developer staff-administration scripts. `DATABASE_URL` is the restricted
`mcr_runtime` login, inheriting the administrator-provisioned `mcr_api` role.
Neither runtime role is a member of the owner role. The migrations require
`mcr_api` to exist; they do not need permission to create login roles or handle
passwords. The local initializer provisions the roles; see the existing-volume
instructions in the deployment guide. Other environments must provision the
same role separation externally before migrating.

US-010/012/015 add `staff_profiles.active` (true by default) and seven auth
tables: `auth_users`, `auth_accounts`, `auth_sessions`, `auth_verifications`,
`auth_two_factors`, `auth_flows`, `auth_rate_limits`. Better Auth rows have UUID
keys generated by Postgres; limiter counters are keyed by HMAC hashes.
These are library/ephemeral records, without business `created_by` attribution.
The nullable unique profile link remains compatible with historical/seed
profiles; the account command creates the account, credential and linked profile
in one transaction with explicit actor attribution. Bootstrap uses the existing
self-reference convention and is allowed only while no auth account exists.

Runtime gets only auth SELECT/INSERT/UPDATE/DELETE; profile activation remains
owner-only. Shared advisory transaction locks serialize sign-in, factor completion
and developer commands without granting runtime activation rights. Existing business/evidence
grants stay intact; runtime cannot create profiles. Developer commands use the
owner connection, never an HTTP administration endpoint. Sessions record native,
pending-native, pending-web or complete-web mode, expiry, last activity and original authentication
time (native: 30 days idle, capped at 90 days; web: 30 minutes idle, capped at 12 hours).
The additive `20261112000000_native_second_factor.sql` migration invalidates
legacy password-only native sessions and pre-change pending state, adds flow-mode
binding and revokes runtime UPDATE(active). Flows store hashed opaque tokens and encrypted internal cookies; the
two-factor plugin encrypts TOTP secrets and backup codes using `AUTH_SECRET`.
All time columns are `timestamptz`. See [the runbook](../docs/runbook.md) for
revocation, factor/password reset and the US-007 audit trail.

`db:migrate` runs dbmate up without a schema dump. `db:generate` introspects the
owner connection with kysely-codegen, formats the result and writes
`api/src/db/generated.ts`. `db:check` regenerates into an external temporary
directory and fails on drift. CI applies migrations twice before checking types.

The seed is idempotent and loads only invented clients and vehicles, attributed
to a self-referencing synthetic staff fixture. It loads no contractual evidence,
terms or real identities. Seed and integration tests require `DB_DISPOSABLE=1`
and fail explicitly when configuration is absent. Integration fixtures remain
in the disposable database; tests use unique identifiers and can run again.
Never target staging or production.

## Physical data and access rules

Client/vehicle snapshots and both pricing groups are flattened typed columns,
not opaque JSON. See [field map](../docs/contract-template/field-map.md) and
[diagrams 05–08](../docs/architecture/README.md). Every amount is `numeric(10,2)`;
only balance may be negative. Fuel is an integer 0–8, km nonnegative, instants
`timestamptz`, names/address lines bounded to 80 and comments to 500 characters.
Card storage is limited to an enumerated brand, four digits and MM/YY expiry.

Column grants prevent runtime status, number/counter and completion-marker
writes, including status on INSERT. Runtime INSERT omits status columns and
uses their defaults. Evidence tables have no UPDATE, DELETE or TRUNCATE grants;
signed revisions, recorded amendments and completed inspections also have row
guards. Unsigned departure revisions and in-progress inspections accept permitted edits. Guards protect
stable damage descriptions and stored drawings even from accidental owner
updates. Terms versions are immutable. Runtime has no business DELETE grants;
future feature functions will implement permitted discards and lifecycle writes.
Database owners remain trusted administrators and can change DDL.

Foreign keys and evidence-link guards validate contract/vehicle/inspection
ownership, photo owner/kind, signature documents/hashes, authorisation references
and version language/kind. Departure damage IDs are checked against the vehicle.
Four-angle baseline completeness, required photos on damage, signature-time
required fields and damage sums will be validated by the feature completion
functions: inserts must permit staged capture. The US-007 migration appends attributed business mutation events; see below.

## Contract numbers

`reserve_contract_number(contract_id uuid, year integer, actor_id uuid)` locks
the contract, atomically increments the year's counter and assigns
`MCR-YYYY-NNNN`. Repeating it returns that contract's existing reservation.
Years are 2000–9999 and sequence values 1–9999; exhaustion fails without assigning
a number. Counter/assignment and caller work share one transaction, so rollback
consumes nothing. The caller supplies the business year, allowing the later
preview function to apply the agency's timezone consistently.

`confirm_contract_number(contract_id uuid, number varchar)` checks the reservation
and records its first confirmation time; retries return the same number. It does
not allocate again or activate the contract. Both functions use fixed search
paths and qualified table names. US-007 revokes their original runtime execute
grants: both are private owner-only helpers. Preview/sign/close/amend/cancel functions, upload
routes and storage policies are separate stories. US-057 will compose confirmation
with signing; preview creation must compose reservation with vehicle holding and
preview registration in one transaction (F-18).

## Audit and server time (US-007; ADR-0007/0012)

`20261117000000_audit_trail.sql` installs `business_mutation_audit`, an AFTER
INSERT/UPDATE/DELETE row trigger on every existing business table. It records
`INSERT`, `UPDATE` or `DELETE`, the table and UUID, exact OLD/NEW JSON, and the
current actor, using database `clock_timestamp()`. The API's `withActor` helper
sets `app.actor_id` with transaction-local `set_config(..., true)` on the same
connection. Missing, empty, malformed or unknown profile actors reject writes;
`created_by` is never a fallback. Commit/rollback clears the setting before pool
reuse. Bootstrap inserts its preallocated, self-attributed profile in that
transaction. Owner scripts/seeds must also set a transaction-local actor.

Excluded relations are `schema_migrations`, `audit_events` (no recursion), and
exactly the seven auth tables listed above. Auth-only sign-in/factor/limiter
transactions have no staff actor: failed attempts must never be attributed to
the targeted account, and no system profile is created. Staff-account commands
always set an actor, including resets whose mutations touch only auth tables.
The owner-only `write_staff_audit` function allowlists the five command actions
and constructs an ID/action-only payload; its failure rolls back the command.
The runtime role can read audit events but cannot insert arbitrary events or
execute that function. Audit timestamps and actor columns are database-stamped.

Signature `signed_at`, stored-signature capture/application/cancellation times,
and creation times on both signature tables are database-owned. Newly recorded
values are stamped; existing evidence times cannot be overwritten. Frozen
revisions/inspections and evidence guards remain in force. Lifecycle functions
belong to their feature stories, including withdrawal and signing.

Every new business-table migration must attach the reusable trigger:

```sql
CREATE TRIGGER business_mutation_audit AFTER INSERT OR UPDATE OR DELETE ON new_table
FOR EACH ROW EXECUTE FUNCTION audit_business_mutation();
```

Catalog tests independently discover tables and fail for missing or disabled
triggers, including future `uploads`, `vehicle_documents` and `auth_*` business
tables. No database-wide privileged event trigger is needed. Keep file bytes
in storage: audit JSON contains paths/IDs, hashes and metadata only. Audit
personal-value anonymisation stays with US-094. Parameterized history queries
for contracts, vehicles, clients and staff accounts are in the runbook.
